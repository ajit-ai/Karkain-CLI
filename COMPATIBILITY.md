## Features verified by this framework

- `func`, untyped parameters, `let`, `return`, `while`, `if`/`else`
- arrays (`[]`, `len`, indexing), strings (`+`, `len`, indexing), `str`,
  `println`, `assert`, `assert_eq`
- `public func` exports and sibling-module `import` + qualified calls
- `getArgs()` builtin: in a binary produced by `karkain build`, index 0 is
  the executable path and subsequent entries are real process arguments
  (verified by building `examples/cli_demo.kark` and invoking it with
  `greet --name Ajit --verbose`)
- `karkain check`, `karkain run`, `karkain build`, `karkain test` and the
  negative-gate exit code 4

## Verified boundaries / limitations

- `karkain run <file>` does **not** forward extra command-line arguments to
  the program; `getArgs()` contains only the generated executable path. Real
  argument consumption therefore requires `karkain build` plus execution of
  the resulting native binary. The verification script exercises that path.
- `karkain test` cannot resolve `import` statements, so native tests are
  generated by concatenating the real module source with the test bodies.
- Local imports resolve from the entry file's directory; the verification
  script stages the module beside the example in a temporary directory.
- The parser in this release is intentionally minimal: option values are
  not distinguished from positionals. `option_value(name)` reads a value by
  option name, while `positional*()` counts every non-dash token. Consumers
  that need strict grammar should build on these primitives.
- `str(bool)` rendering differs between the `karkain run` path (1/0) and the
  compiled native binary (`true`/`false`); tests avoid asserting on that
  rendering.
- The test driver emits non-fatal Winsock linker diagnostics on this Windows
  host; failure detection was verified separately with an `assert(false)`
  case returning exit code 4.

No claim is made about Linux, macOS, mobile, WASM, GPU, NPU, quantum or
network support for this framework.

## Scope boundary

The Karkain toolchain CLI is part of the language distribution and was not
modified. This framework supplies only portable building blocks for a user
program's own argument surface; it does not replace compiler commands or
invent new toolchain flags.
